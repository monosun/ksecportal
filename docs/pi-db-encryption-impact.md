# DB 개인정보 암호화 영향도 검토

> 작성일 2026-08-01 · 대상 버전 v1.28.0
> 화면 표시 마스킹(v1.28.0)은 "보여주는" 단계의 보호이고, 이 문서는 "저장하는" 단계까지 암호화할 경우의 영향도를 정리한다.
>
> **검토 결과 3안(하이브리드)을 v1.28.0 에 적용했다.** 적용 내용은 [6. 적용 결과](#6-적용-결과-v1280)를 참고한다.

## 1. 지금 DB에 저장되는 개인정보 (실측)

| 테이블 | 컬럼 | 성격 | 조회·검색에 쓰이는 방식 |
|--------|------|------|------------------------|
| `users` | `email` `varchar(255)` **UNIQUE** | 임직원 계정 | 로그인 `findByEmail`, 중복확인 `existsByEmail`, Okta 계정 매칭 |
| `users` | `name`, `department` | 임직원 | 목록 표시, 부서 통계 |
| `privacy_contractors` | `business_number`, `representative`, `contact_person`, `contact_email`, `contact_phone` | 수탁사 담당자 | 목록 전체 조회 후 **화면(클라이언트)에서 필터** |
| `privacy_rights_requests` | `subject_name`, `contact` | **외부 정보주체** | 목록 전체 조회 후 **화면에서 필터** |
| `phishing_targets` | `name`, `email` | 임직원 | 목록 조회, 중복확인 `existsByEmail` |
| `audit_logs` | `ip_address` (326건) | 접속 IP | 목록 표시 |
| `slow_logs` | `ip_address` | 요청 IP | 목록 표시 |

**법령상 암호화 의무 대상은 현재 저장하지 않는다.** 개인정보보호법 시행령 제30조·안전성 확보조치 기준이 암호화를 의무화한 값은 고유식별정보(주민등록번호 등)·비밀번호·바이오정보·신용카드번호·계좌번호인데, 이 포털의 실데이터에는 없다(코드관리의 해당 항목들은 "조직이 처리하는 개인정보 항목의 기준 정의"이지 저장 데이터가 아니다). 비밀번호는 이미 BCrypt 단방향 해시다.

→ 따라서 DB 암호화는 **법적 의무 이행이 아니라 심층 방어(선택)** 이며, 얻는 것과 잃는 것을 견줘 범위를 정하면 된다.

## 2. 방식별 영향도

### A. 애플리케이션 컬럼 암호화 — 전 컬럼 적용 (영향 큼, 비권장)

JPA `AttributeConverter`(AES-GCM)로 위 컬럼을 모두 암호화하는 경우.

| 영역 | 영향 |
|------|------|
| **로그인** | `users.email` 은 UNIQUE 인덱스 + `findByEmail` 조회 키. AES-GCM은 매번 IV가 달라 **같은 값이 다른 암호문**이 되므로 조회 실패·유니크 제약 붕괴. 결정적 암호화(고정 IV)나 블라인드 인덱스(해시 컬럼 + 유니크) 추가가 **필수** |
| **중복확인** | `phishing_targets.existsByEmail` 도 같은 문제 |
| **검색** | 서버 `LIKE` 검색을 쓰는 화면(자산·인시던트·정책·SBOM 등)은 개인정보 컬럼을 쓰지 않아 무관. 개인정보 화면(수탁사·정보주체 권리행사)은 **이미 클라이언트 필터**라 영향 없음 |
| **정렬·집계** | 이름 정렬, 부서별 집계는 암호문 기준이 되어 무의미해짐(`department` 암호화 시 `GROUP BY` 통계 붕괴) |
| **스키마** | 암호문(Base64)은 원문의 약 2배 이상. `ddl-auto: update` 는 **컬럼 길이를 늘려주지 않으므로** `db/migration/*.sql` 수동 마이그레이션 + `db/init/*.sql` 동시 수정 필요 |
| **기존 데이터** | 평문 → 암호문 **백필 배치**가 필요(앱에서만 암·복호 가능하므로 SQL 단독 불가). 백필 중 장애 시 평문/암호문 혼재 → 평문 감지 후 암호화하는 멱등 러너로 설계해야 함 |
| **키 관리** | 키 분실 = **데이터 영구 손실**. 기존 Jasypt 마스터 키와 같은 체계를 쓰면 키 불일치 시 기동 실패(v1.27.0 경험) 범위가 설정값에서 업무 데이터로 확대 |
| **백업·복원** | `BackupService` 는 `SELECT *` → JSON → gzip. 암호문 그대로 백업되어 **백업 파일 보호는 강화**되지만, 복원 대상 인스턴스가 **같은 키**를 가져야 복구 가능 |
| **성능** | 행당 복호화 비용은 µs 단위로 무시 가능. 실제 비용은 인덱스를 못 타는 조회가 생길 때의 풀스캔 |
| **부수 기능** | 사용자 CSV/PDF 내보내기·메일 발송·리포트는 복호화된 엔티티를 쓰므로 코드 변경 없이 동작 |

### B. MySQL 투명 암호화(TDE / 볼륨 암호화) — 영향 거의 없음, 보호 범위도 좁음

- InnoDB 테이블스페이스 암호화 또는 호스트 디스크·볼륨 암호화.
- **애플리케이션·쿼리 영향 0.** 검색·정렬·유니크·통계 모두 그대로.
- 막아주는 위협은 **디스크·백업 파일 유출**뿐이다. DB 계정 탈취, SQL Injection, 앱 권한 오남용에는 아무 효과가 없다.
- MySQL 8 CE에서는 `component_keyring_file` 구성이 필요하고, keyring 파일을 잃으면 테이블을 못 연다(도커 볼륨에 별도 보관·백업 필요).

### C. 하이브리드 — 고위험 소수 컬럼만 앱 암호화 (권장)

암호화 대상을 **조회 키·정렬·집계에 쓰이지 않는 컬럼**으로 한정한다.

| 대상 | 사유 | 예상 영향 |
|------|------|-----------|
| `privacy_rights_requests.subject_name`, `contact` | **외부 정보주체** 정보로 민감도가 가장 높음 | 서버 쿼리에서 쓰이지 않음(목록 조회 후 화면 필터) → **영향 없음** |
| `privacy_contractors.contact_person`, `contact_email`, `contact_phone`, `business_number` | 외부 담당자 연락처 | 동일하게 서버 검색·정렬 대상 아님 → **영향 없음** |
| **제외**: `users.email` | 로그인 키·UNIQUE·Okta 매칭 | 암호화하려면 블라인드 인덱스 도입이 선행돼야 하므로 접근통제·마스킹으로 대응 |
| **제외**: `users.name/department`, `audit_logs.ip_address` | 정렬·통계·대량 로그 | 이득 대비 부작용이 큼. 화면 마스킹(v1.28.0)으로 커버 |

필요 작업: `AttributeConverter` 1개 + `@Convert` 6컬럼 + 컬럼 길이 확대 마이그레이션(`db/migration` + `db/init`) + 멱등 백필 러너 + 키 주입·백업 문서화. **기능 회귀 위험은 낮고**, 화면·API 변경은 없다.

## 3. 결론

1. 현재 저장 데이터에는 **법적 암호화 의무 대상이 없다.** 화면 마스킹(v1.28.0) + 접근통제 + 감사로그로 기준은 충족한다.
2. 추가 보호가 필요하면 **C(외부 개인정보 6개 컬럼만 앱 암호화)** 가 비용 대비 효과가 가장 좋다. 검색·로그인·통계에 손대지 않는다.
3. **B(볼륨/TDE)** 는 A·C와 배타적이지 않으므로, 디스크·백업 유출 대비로 함께 적용할 수 있다.
4. **전 컬럼 암호화(A)** 는 로그인 조회 키까지 건드려야 해서 블라인드 인덱스 설계가 선행되지 않으면 권하지 않는다.
5. 어느 방식이든 **키 분실 = 복구 불가**다. 마스터 키는 백업본과 **분리 보관**하고, 복원 절차 문서에 "같은 키가 있어야 복원된다"를 명시해야 한다.

## 6. 적용 결과 (v1.28.0)

3안(하이브리드)을 적용했다.

### 암호화된 컬럼

| 테이블 | 컬럼 |
|--------|------|
| `privacy_rights_requests` | `subject_name`, `contact` |
| `privacy_contractors` | `business_number`, `contact_person`, `contact_email`, `contact_phone` |

- 알고리즘 **AES-256-GCM**, 저장 형식 `PIENC1:` + Base64(IV(12B) ‖ 암호문 ‖ 인증태그). 매번 IV가 달라 같은 값도 다른 암호문이 된다.
- 키는 `PI_ENCRYPTION_KEY`(없으면 Jasypt 마스터 키)의 SHA-256. `PI_ENCRYPTION_KEY_FILE` 로 파일 주입도 가능하다.
- `users.email/name`, `audit_logs.ip_address` 는 **제외**했다(로그인 조회 키·정렬·대량 로그). 이들은 화면 마스킹으로 보호한다.

### 구성 요소

| 파일 | 역할 |
|------|------|
| `common/crypto/ColumnCipher.java` | 암·복호화. 접두어 없는 값은 평문으로 보고 그대로 통과(백필 중·구 백업 복원 직후 호환). 복호화 실패 시 화면에는 `(복호화 실패)` 를 보이고 원문은 DB에 보존 |
| `common/crypto/EncryptedStringConverter.java` | JPA `AttributeConverter` — 엔티티 필드에 `@Convert` 로 적용 |
| `common/crypto/ColumnCipherConfig.java` | `application.yml` 의 `app.privacy.column-encryption.*` 주입 |
| `common/crypto/PiColumnEncryptionBackfill.java` | 기동 시 남은 평문을 암호화. 이미 암호문이면 건너뛰므로 **매 기동 반복 실행 안전**. 컬럼 길이가 부족하면 건너뛰고 ERROR 로그로 마이그레이션을 안내 |
| `db/migration/v1.28.0_pi_column_encryption.sql` | 컬럼 길이 확대(512자, 사업자번호 255자). **기존 DB는 반드시 실행** |

### 운영 시 주의

- **키를 잃으면 복구 불가.** 백업본과 분리 보관하고, 키 교체는 "구 키로 복호화 → 신 키로 재암호화" 배치가 별도로 필요하다(현재 미구현).
- 백업(`SELECT *` → JSON → gzip)에는 **암호문 그대로** 담기므로 백업 파일 유출 시에도 안전하다. 반대로 **복원 대상 인스턴스에 같은 키가 없으면 복호화되지 않는다.**
- v1.28.0 이전에 만든 평문 백업을 복원하면 평문 행이 들어오지만, 재기동 시 백필이 다시 암호화한다.
- 암호화된 컬럼은 서버 쿼리에서 검색·정렬·집계에 쓰이지 않는다. 해당 화면의 검색은 목록을 받아 브라우저에서 거르는 방식이라 영향이 없다.
